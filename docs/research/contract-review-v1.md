# QuietClerk 엔진 계약 독립 검토

## 판정·범위

**현재 계약 그대로 M1 전체를 구현 에이전트들에게 병렬 배정하는 것은 불가다.** 방향에는 동의한다. 단일 실행자, 실행별 설정, 언어 중립 키, 동의·백업, 로컬 전용 모드, 입력 방침 표는 지난 검토보다 분명해졌다. 그러나 데이터 이행·작업 소유권·노트 갱신·외부 전송의 안전 경계는 아직 구현자마다 다르게 해석할 수 있다(`docs/contracts.md:30-44,98-138,291-363`). 아래 수정은 기능 확대가 아니라 이미 약속한 동작을 구현 가능하게 만드는 제안이다.

- 직접 읽은 범위: 계약 전체, 설계 v2 전체, 지난 검토, `rec`의 DB/설정/intake/tick/models/transcript/postprocess/render/llm/backfill/syncthing, 기존 테스트 3종, 배포·공개 export, 운영·인수 문서. 프로젝트 파일·운영 서비스는 변경하지 않았다.
- **검증 수준: 정적 열람만.** 실행만: 없음 / 가정으로 확인한 실행: 없음 / 실제 입력으로 확인한 실행: 없음. 코드에서 따라간 경로는 실행 증명이 아니다. 발생 가능성·미재현 결과에는 `[추정]`을 붙였다.
- 운영 Mac mini에 v1 DB·`~/rec`·한국어 키 노트가 있다는 사용자 관찰을 전제로 한다. 운영 경로는 `docs/operations.md:6-18`, 실제 경로 기록은 `docs/acceptance.md:7`로 교차 참조했으며, 원격 DB·볼트를 열거나 재현하지 않았다.
- 아래 **닫힘**은 설계 요구가 명시됐다는 뜻이지 구현·제품 게이트 통과라는 뜻이 아니다. 계약 밖 출시 요구는 v2 문서의 명시적 담당 작업으로 위임됐는지도 함께 판단했다.

## 2. 계약 수정 지적

### R01 [치명적] v1→v2 이행은 백업·변환 규칙이 부족하다

**지적 →** ‘DB 파일 복사’는 WAL DB의 일관된 백업 계약이 아니다. 기존 `jobs/files`와 동일 이름으로 새 테이블을 어떻게 교체할지, v1의 필드를 어떻게 보존할지도 없다.

**근거 →** 계약 `:100-132`; v1 `rec/db.py:7-28,34-40`은 WAL이고 `recorded_at/source/sha256(files)/runs`가 없으며 `warnings/output_path/error`가 있다. SQLite는 커밋이 본 DB가 아닌 WAL에만 있을 수 있음을 설명한다([WAL 동작](https://www.sqlite.org/wal.html#how_wal_works)); 일관된 복사는 [Backup API](https://www.sqlite.org/backup.html#using_the_sqlite_online_backup_api)로 제공한다. `[추정]` 본 파일만 복사하면 마지막 작업이 빠진 백업을 만들 수 있다.

**고칠 문장 →**
> 이행은 구 실행자를 정지·회수하고 이행 배타 잠금을 얻은 뒤 한 번만 수행한다. 백업은 Python sqlite3의 Backup API로 별도 파일에 완성한 후 확정한다. `meta`가 없는 알려진 v1 구조만 v1로 인정하고, 알 수 없는 구조·더 높은 버전은 쓰기 없이 중단한다. `_v2` 임시 테이블에 변환 후 같은 트랜잭션에서 교체한다. `output_path→note_path`, `error→last_error/skip_reason`, `warnings→review_reasons`를 보존한다. `recorded_at`은 기존 job_id의 시각을 보존하며 재해석하지 않는다. 기존 `failed_retryable`은 `retry_wait`, `failed_final`은 `failed`; 재시도 시각은 기존 backoff 의미를 보존한다. 기존 `running`은 이행 중 interrupted로 정리하며 attempts는 늘리지 않는다. v1 결과는 legacy 결과로 보존하되 설정·모델 revision을 추정해 유효 캐시로 승격하지 않는다. `files.source`는 이행 기원으로 기록하고 알 수 없는 sha는 NULL을 유지한다.

`current_run_id`에 가짜 성공 run을 만들지 말고 legacy 표시·NULL 허용을 명시하자. 백업 세대 삭제는 새 버전의 복구 가능한 백업이 확보된 뒤에만 한다. 전 연결의 `foreign_keys=ON`, 상태 CHECK, 같은 job의 active run 유일성도 DDL에 포함해야 한다(`docs/contracts.md:117-131`).

### R02 [치명적] 루트 이동·설정 변환·서비스 교체는 하나의 cutover여야 한다

**지적 →** `~/rec`를 옮기고 Syncthing 경로를 바꾼다는 한 문장으로는 운영 설치를 안전하게 이전할 수 없다. `ROOT/serve.lock`만으로는 다른 ROOT의 두 서비스 또는 기존 tick과의 동시 실행을 막지 못한다.

**근거 →** 계약 `:22-23,136-138`; 기존 배포는 `~/rec/app/.venv`, plist의 절대 실행/작업 디렉터리, `REC_LABEL`과 `tick.lock`을 쓴다(`deploy/install.sh:13-20`, `deploy/setup.sh:7-9,17-40`, `deploy/launchd.plist.in:7-14`, `rec/config.py:36-43`). DB의 archive 경로는 문자열로 저장된다(`rec/intake.py:87-99`). `[추정]` 폴더만 이동하면 DB·venv 실행 경로·서비스·Syncthing이 서로 다른 위치를 가리킨다.

**대안 비교 →** ①업그레이드와 동시에 무조건 이동: 장애 범위가 크다. ②기존 루트에서 먼저 cutover한 뒤 명시적 이동 명령: **추천**, 현재 동의 전 유지 결정에도 부합한다. ③영구 심볼릭 링크/양쪽 호환: 두 경로와 잠금의 소유권을 남기므로 비추천.

**고칠 문장 →**
> 업그레이드는 기존 사용자 루트를 그대로 채택한다. 루트 이동은 별도 동의된 유지보수 작업으로 수행한다. 설치된 구 label(사용자 지정 label 포함)을 unload하고 tick 잠금 획득과 구 프로세스·자식 종료를 확인한 뒤 신 서비스를 시작한다. 사용자별 고정 위치의 서비스 잠금은 ROOT 변경과 무관하다. 이동 시 Syncthing 대상 폴더를 일시정지하고 DB 연결을 닫은 뒤 파일·DB 내부 경로·설정·서비스 경로를 일괄 갱신한다. venv는 단순 이동을 가정하지 않고 새 위치에서 재구성한다. 외부 사용자 지정 경로는 바꾸지 않는다. 양쪽 루트가 있으면 자동 병합·빈 DB 생성 없이 충돌을 보고한다. 실패 시 구 설정·서비스·Syncthing 경로로 되돌리며, 성공 전 구 실행 재등록을 금지한다.

### R03 [높음] claim UPDATE만 원자적이며 실행 생성·모드 저장은 원자적이지 않다

**지적 →** claim 행 경쟁 방지는 맞다. 그러나 run 생성·설정 스냅샷과 한 트랜잭션이라는 규정이 없다. API가 `done→queued`로 바꾼 뒤 재시작하면 `resummarize` 모드를 어디서 복구할지도 없다. `current_run_id`는 마지막 성공이므로 현재 실행 식별자로 쓸 수 없다.

**근거 →** 계약 `:35-44,91,115-129,147,175-178`. `jobs`에는 요청 모드나 active run이 없고 `runs.mode`만 있다. `[추정]` claim 직후 종료하면 running job에 대응하는 run/설정이 없거나 재처리 모드가 auto로 바뀐다.

**고칠 문장 →**
> `jobs`에 `requested_mode`, `active_run_id`를 둔다. process 요청은 허용 상태 검사·requested_mode 저장·attempts/interrupt_count/next_attempt_at 초기화를 한 트랜잭션으로 처리한다. claim은 `BEGIN IMMEDIATE` 안에서 `(created_at, job_id)` 순으로 대상 선택, 조건부 UPDATE, run 삽입, 설정/override 스냅샷 저장, active_run_id 설정을 함께 커밋한다. rowcount=0이면 run을 만들지 않는다. 단계·완료·실패 쓰기는 job_id뿐 아니라 active_run_id와 claimed_by가 같은 경우에만 반영한다. current_run_id는 마지막 게시 성공 실행 전용이다.

조건식은 최소 `status='queued' OR (status='retry_wait' AND next_attempt_at<=:now)`로 구분하고, 뒤 R04의 사용자 조치 대기는 claim 대상에서 제외한다. API는 이 트랜잭션 함수를 호출할 뿐 자체 UPDATE를 만들지 않아야 한다.

### R04 [높음] 상태 기계·복구·제외·단계 이력이 아직 닫혀 있지 않다

**지적 →** no_speech 전이, 진행 중 제외 요청의 저장, interrupted stage 처리, 연속 중단 초기화, attempts=3 전이의 증가 시점이 미정이다. `claimed_by != boot`는 NULL인 running 행을 선택하지 않는다.

**근거 →** 계약 `:39,83-96,117-129,238,282-285,359`. stage_runs에는 running/interrupted/cancelled가 없고 runs에는 skipped/cancelled가 없다. `retry_wait`의 사용자가 즉시 재시도하는 전이도 없다.

**고칠 문장 →**
> 재시도 가능한 처리 실패 한 번마다 `new_attempts=attempts+1`을 계산해 3 미만은 retry_wait, 3 이상은 failed로 한 번에 기록한다. 중단은 attempts를 늘리지 않고 interrupt_count만 늘리며, 정상 종료한 실행 또는 명시적 새 처리 요청에서 연속 중단 카운터를 초기화한다. 복구 대상은 `claimed_by IS NULL OR claimed_by<>:boot`; 대응 run/stage도 interrupted로 종료한다. stage 상태에 running/interrupted/cancelled, run 상태에 skipped/cancelled를 추가한다. `running→skipped(no_speech)`를 허용한다. running 제외 요청은 `exclude_requested=1`로 영속화하고 다음 단계 시작·외부 호출·노트 게시 전에 검사한다. 현재 단계가 끝나면 이후 단계 없이 skipped(user_excluded)로 끝낸다. pause는 새 claim만 막는다.

인증/제공자 부재는 일반 실패와 분리하자: `retry_wait`에 `blocked_reason`을 두고 `auth/no_local_provider`는 타이머로 소진하지 않으며 인증·설정 변경 또는 명시적 process 요청으로만 해제하는 안을 추천한다. 이를 택하면 `retry_wait→queued`, blocked 작업의 선택 조건도 표에 넣어야 한다. R13과 같은 문구를 써야 한다.

### R05 [높음] 해시 없는 거부 입력의 저장 모델과 skipped 승격이 충돌한다

**지적 →** 크기 검사에서 즉시 거부하면서 `sha256 NOT NULL`인 job에 `skipped(too_big)`를 남기려면 금지하려던 대형 파일 해시를 다시 읽어야 한다. ‘사유만 빼고 재검증’은 too_big/format/decode도 우회하는지 불분명하다.

**근거 →** 계약 `:85-95,102-109,256,262-275`; 현재 skipped는 아카이브 없이 해시·가상 archive_path만 남긴다(`rec/intake.py:78-99`). 파일 변경 시 handled는 초기화된다(`rec/db.py:43-51`). `[추정]` 같은 이름이 다른 내용으로 교체된 후 승격하면 기존 job의 해시와 다른 음성을 처리할 수 있다.

**대안 비교 →** ①거부 파일도 전부 해시: 조기 한도 취지 훼손. ②job.sha를 nullable로: ‘한 해시 한 job’ 정의 약화. ③해시 전 거부는 files의 수집 상태로 기록: **추천**.

**고칠 문장 →**
> files에 수집 상태·거부 사유를 두며, 해시 전 크기/형식/디코드 거부는 작업이 아닌 거부된 입력으로 기록한다(IN-10/11/13의 기대 상태도 함께 변경). job은 안전하게 확인한 전체 SHA-256이 있을 때만 생성한다. 사용자가 우회할 수 있는 정책은 too_short와 before_cutoff뿐이다. user_excluded는 명시적 제외 해제로 처리한다. 크기·형식·경로·코덱 제한은 어떤 요청으로도 우회하지 않는다. skipped 승격은 현재 원본의 전체 해시가 기존 job.sha256과 같은지 확인한다. 다르면 기존 job은 그대로 두고 새 입력으로 등록한다. 같은 해시의 다른 경로는 files.sha256으로 찾고, 안정된 원본 하나를 선택한다.

‘NFC/NFD가 같은 이름’은 표시·선택 비교 규칙이지 내용 식별자가 아니다. 정규화 이름 충돌은 전체 해시로 구분하고, SHA 접두어 기반 job_id 충돌 시 덮어쓰기 없이 더 긴 식별자로 확장하도록 명시한다(현 생성 규칙 `rec/intake.py:86-87`).

### R06 [높음] 캐시 키·강제 무효화·하드링크의 불변성 범위가 불완전하다

**지적 →** transcribe 예시 하나로는 단계별 입력/params가 고정되지 않는다. note는 사용자 파일이라는 가변 입력이라 다른 artifact처럼 단순 재사용하면 안 된다. 언어 변경으로 ASR 출력 바이트가 우연히 같으면 입력 해시 비교만으로 후속 전부 무효화가 보장되지 않는다.

**근거 →** 계약 `:150-180,249,319-335`. 현재 classify는 파일명·프로젝트 목록을, summarize는 분류 메타를 읽는다(`rec/postprocess.py:118-128,162-172`). ASR에는 aligner도 관여한다(`rec/models.py:33-44`). `[추정]` 출력 언어/aligner/프로젝트 목록 변경이 누락된 캐시 키로 이전 결과를 재사용할 수 있다.

**고칠 문장 →**
> 단계별 입력·params 표를 고정한다. convert에는 원본 SHA와 변환 규격/버전, transcribe에는 오디오·처리 언어·ASR/aligner의 revision·분할/정렬 인자, turns에는 ASR/diarize 해시와 결합 규칙 버전, correct에는 turns/second_pass·프롬프트·언어·제공자/모델 설정, classify에는 교정 결과·source_name·정렬된 프로젝트 목록, summarize에는 교정 결과·분류 메타·노트 출력 언어·양식 버전을 넣는다. 재사용 정책에는 현재 허용 제공자 정책도 포함한다. 언어/프롬프트 변경 및 강제 재처리 모드는 지정 단계와 모든 파생 단계의 재사용을 금지한다. note는 매번 현재 사용자 파일과 병합·소유권 검사하며 캐시 파일을 그대로 게시하지 않는다.

> artifact는 output_sha256와 원본 producer run/stage를 기록한다. 데이터 rename 후 메타를 마지막에 확정하고 메타 없는 데이터는 재사용하지 않는다. 하드링크한 파일은 불변이며, 새 결과는 새 임시 파일에서 rename한다. 재사용 이력은 원래 생성 제공자와 이번 전송 없음(sent_fields=[])을 구분한다. v1의 메타 없는 파일은 보존만 하고 재사용하지 않는다.

### R07 [높음] 노트 파일·소유권 sidecar·DB 성공 포인터의 게시 원자성이 없다

**지적 →** 각 파일 rename은 원자적이어도 노트+sidecar+DB 세 개를 한꺼번에 바꾸지는 않는다. ‘실패해도 이전 노트 그대로’는 현재 문장만으로 보장되지 않는다.

**근거 →** 계약 `:88,147-148,319,334`; 현재 코드는 노트를 쓴 뒤 classify/summary 실패를 던진다(`rec/tick.py:139-158`). `[추정]` 새 노트 rename 후 DB 커밋 전 종료하면 UI는 구 실행, 볼트는 신 실행, 소유권 기억은 구 값일 수 있다.

**고칠 문장 →**
> 모델 단계 성공과 노트 게시를 구분한다. 게시 전에 대상 경로·기존 파일 해시·새 파일 해시·소유권 변경을 durable publish record로 저장한다. 현재 파일이 읽은 해시와 달라졌으면 덮어쓰지 않고 note_conflict로 끝낸다. 새 노트 확정 후 소유권 메타와 current_run_id를 커밋하고 게시 기록을 완료한다. 시작 복구는 파일 해시와 게시 기록으로 이미 완료된 게시를 마무리하며 LLM을 다시 호출하지 않는다. 게시 시작 전 실패는 이전 노트를 보존한다. 게시 시작 후 중단은 실패로 단정하지 않고 복구 대상이다. 표식 부재/중복/충돌로 게시를 못 하면 done으로 표시하거나 마지막 성공 포인터를 바꾸지 않는다.

구현을 단순화하려면 sidecar 대신 소유권 메타를 같은 SQLite에 두는 대안도 있다. 그러나 파일과 DB 경계는 남으므로 복구 기록 자체는 필요하다. E2/E3와 E7의 인터페이스로 먼저 고정할 것.

### R08 [높음] 노트 소유권 판정에 영속 소유자·식별 충돌·사용자 편집 경합이 빠졌다

**근거 →** 계약 `:298-319,340-342`; 기존 탐색은 앞 4000자의 정규식 첫 매치만 반환한다(`rec/render.py:66-76`). 제목 본문은 generated 바깥에 있다(`docs/contracts.md:325-334`). `[추정]` 복제 노트·수동 이름 변경·동기화 경합에서 임의 파일을 덮어쓰거나 사용자 제목을 되돌릴 수 있다.

**고칠 문장 →**
> 소유권은 필드별 owner(engine/user), last_generated_value, last_published_file_hash로 영속화한다. 현재 값이 마지막 생성값과 다르면 user로 전환하며 명시적 ‘자동 관리로 돌리기’ 전에는 되돌리지 않는다. 소유권 기록이 없으면 기존 title/division은 사용자 소유로 취급한다. 사용자 필드의 빈 목록도 사용자 값이며 생성 시에만 기본값을 넣는다. 알 수 없는 frontmatter 키는 보존한다. 노트 식별은 parsed frontmatter의 qc_schema=2, job_id, source_sha256과 DB 대응을 확인한다. 경로가 바뀌면 볼트 범위 안에서 재탐색하고, 일치 파일이 여러 개면 자동 선택하지 않는다. 사용자 소유 파일·symlink·볼트 밖 경로는 덮어쓰지 않는다.

본문 `# title`·info를 갱신할 것인지도 결정해야 한다. 추천 문장: ‘자동 title/info는 별도 생성 표식 안에서 관리하고, title 소유권이 user면 제목 표시도 사용자 값으로 렌더한다. 나머지 사용자 영역은 바이트 그대로 보존한다.’

이 UI/본문 정책 변경은 계약에 명시해 합의해야 하며, 구현자가 몰래 ‘같은 문장일 때만 보존’으로 범위를 줄이면 안 된다.

### R10 [높음] 기존 노트 이행의 ‘속성만’ 전략은 안전하지만 재처리 종료 상태를 정의하지 않았다

**고칠 문장 →**

### R11 [높음] 언어 판정은 짧은 발화를 침묵으로 오인할 수 있고 집계식도 미정이다

**지적 →** ‘5초 이상 단일 화자 구간 없음’은 ‘음성 없음’과 같지 않다. 구간 길이 가중이 최다 언어 투표인지 후보 점수의 가중 평균인지 불분명하다. override로 감지를 건너뛰면서 감지 결과를 기록한다는 문장도 양립하지 않는다.

**근거 →** 계약 `:166-171,228-249,303`. 실제 언어 판별은 diarize 결과에 의존하는데 DAG에는 그 화살표가 없다. second_pass(lang)도 detect_language 의존선이 없다. `[추정]` 짧은 문답이 계속되는 회의는 no_speech로 건너뛸 수 있다.

**고칠 문장 →**
> 발화 구간은 화자 경계를 합친 발화 시간 집합으로 표집한다. 6개 시간 구간과의 교집합을 만들고 최대 20초로 잘라 중복 표집하지 않는다. 5초 이상 구간이 없어도 발화가 있으면 사용 가능한 짧은 구간을 사용하며, 표본 부족은 uncertain이다. no_speech는 발화가 없다는 별도 판정에서만 사용한다. 몫은 `share(l)=Σ d_i·1[argmax(score_i)=l]/Σ d_i`로 정의한다(d_i는 실제 표집 길이). 동률 규칙·누락 점수·빈 결과를 고정하고, 점수를 정확도 확률로 표시하지 않는다.

> job override > 전역 고정 > 자동 감지 > 기본 언어 순이다. 고정 언어면 detect 상태는 not_run, language_detected는 null이며 과거 감지값을 이번 감지값처럼 쓰지 않는다. 감지 산출물은 status/top_language/shares/windows를 기록한다. DAG는 diarize→detect_language→transcribe/second_pass이다. 노트 출력 언어는 별도 값으로 남기고 프롬프트·검증·렌더 캐시 키에 포함한다.

점수 가중 평균을 선택해도 되지만 위 투표식과는 다른 알고리즘이다. 어느 쪽이든 표본으로 조정하기 전 계약에서 하나를 선택해야 한다. 감지 임계값의 품질은 이번 검토로 검증하지 않았다.

### R12 [중간] Backend·worker·설정 스냅샷의 실제 전달 규격이 필요하다

**지적 →** Python Protocol은 있으나 worker가 어떤 설정/모델 revision을 받아 어떻게 결과를 보장하는지 없다. 마지막 stdout 한 줄만 metadata로 쓰면 라이브러리 출력과의 구분이 불명확하다. Ollama HTTP 요청은 CLI 프로세스 그룹과 종료 방식이 다르다.

**근거 →** 계약 `:18-19,43,56-57,199-220`; 기존 worker는 CLI 인자 3개와 import-time config를 쓴다(`rec/models.py:13,71-78`), backend에는 모델 설정 인자가 없다. transcribe/aligner는 둘 이상의 모델을 쓴다(`rec/models.py:33-44`).

**고칠 문장 →**
> worker는 run의 읽기 전용 설정 파일 경로, stage, 입력/출력 경로를 인자로 받으며 환경 설정을 다시 합성하지 않는다. 결과 JSON은 typed payload와 단계가 사용한 모든 model ID/revision을 포함한다. stdout은 type 필드가 있는 progress/result 이벤트, 일반 로그는 stderr로 분리한다. 시간은 유한한 초 단위이며 `0≤start≤end≤duration`, 단어 정렬 기준과 겹침/동률 처리, 빈 단어 정규화, 무효 출력 오류를 고정한다. BackendUnavailable/ModelMissing 등의 구조와 재시도 분류를 공통 계층이 해석한다. CLI·모델 worker만 소유 프로세스 그룹을 종료하고 Ollama timeout은 요청을 취소한다. 공유 Ollama 서버나 다른 사용자 작업은 종료하지 않는다.

이것은 백엔드 추가 추상화가 아니라 `runs.settings_json`만 본다는 계약을 실제 worker까지 연결하는 규격이다.

### R16 [높음] 로컬 인증 부트스트랩·LAN 모드·API 요청 의미가 덜 고정됐다

**지적 →** `open`이 토큰을 얻는 신뢰 경계가 없다. 누구나 HTTP로 토큰을 발급받는 구현도 문장상 배제되지 않는다. URL 토큰 교환과 상태 변경 GET 금지가 혼재하고, LAN을 켜도 Host 규칙은 localhost 둘만 허용한다. 삭제·작업별 언어 고정 API도 없다.

**근거 →** 계약 `:114,186,371-391`; v2 `:102,218,310`. `[추정]` 구현자마다 인증 예외와 원격 권한이 달라지거나 UI 요구를 별도 DB 쓰기로 우회할 수 있다.

**고칠 문장 →**
> open의 bootstrap token은 같은 OS 사용자에게만 허용된 로컬 IPC/0600 capability로 발급한다. 인증 없는 HTTP 토큰 발급은 없다. 브라우저에는 fragment로 전달하고 로컬 번들 JS가 주소에서 즉시 제거한 뒤 POST로 일회 교환한다. 교환에도 Host/Origin을 검사한다. 세션은 암호학적 난수, HttpOnly/SameSite=Strict/Path=/, 만료·폐기 규칙을 가진다. TLS 모드에는 Secure를 적용하고 bootstrap 응답은 no-store와 no-referrer를 설정한다. GET/audio/SSE도 인증을 우회하지 않는다.

> M1은 loopback-only로 고정하고 LAN 설정을 비활성화한다. LAN 활성화 작업에서는 허용 Host·TLS·장치 권한·폐기·토큰 발급 규칙을 별도 완성해야 한다. settings/process의 JSON 스키마·허용 키·오류 코드·중복 요청 의미를 정의한다. 작업 언어 override와 로컬 데이터 삭제의 인증된 변경 endpoint를 명시한다. audio는 DB에서 찾은 검증된 archive 파일만 제공하며 파일 없음·삭제·권한 없음과 잘못된 Range(416)를 구분한다. 경로 입력을 파일 경로로 직접 결합하지 않는다.

이는 이미 v0.2 LAN을 꺼도 된다는 결정(`:391`)을 명확한 착수 범위로 고정하는 제안이다. CSP에는 최소 `object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'`도 명시하고 본문 링크의 내부 경로 범위를 고정하자.

**지적 →** `-protocol_whitelist file`은 네트워크 프로토콜 제한이지 로컬 파일 접근 경로 제한이 아니다. probe 뒤 convert에는 같은 제한도 명시되지 않았다. 2GB 미만에서 실행만 멈추면 스캔이 계속 아카이브를 만들어 공간을 소진할 수 있다.

**고칠 문장 →**

## 4. M1 작업 순서·파일 소유권

기존 작업 그래프는 `docs/product-design-v2.md:281-300`이다. 아래 파일은 현재 경로 기준이며 rename 뒤 같은 소유권을 유지한다. 새 분리 파일 이름은 구현 팀이 정하되 기존 파일을 여러 에이전트가 동시에 고치지 않는다.

### 4.1 먼저 고정할 문서

1. **main: C1 수정** — R01–R19의 선택을 계약/DDL/상태표/설정표에 반영하고 상충하는 v2 문장을 함께 고친다. 실제 안전 보장 미결은 main의 S3·표본 일정에 남긴다.
2. **E1a의 기계적 namespace cutover를 단독 한 번** — `rec→quietclerk`, pyproject, import, worker, deploy, 테스트 격리 설정, export, 명령 문서. 다른 에이전트가 구 경로에서 작업을 시작한 뒤 rename하지 않는다. 기능 구현과 배포 실행은 별개다.
3. **E3a + E2a의 저장·상태 인터페이스 확정** — API/모델/노트 에이전트가 직접 DB 쓰기를 만들어내기 전에 공용 전이·스냅샷·게시 계약을 제공한다.

### 4.2 배정 묶음

| 단일 소유자 묶음 | 포함 작업·파일 | 묶는 이유·선행 |

패키지 의존성·entrypoint를 담는 `pyproject.toml`과 공개 export는 **E1 담당 한 명만** 쓴다. 모델/제공자 에이전트는 필요한 변경을 전달한다. `docs/contracts.md`와 v2 작업표는 main 소유로 둔다. 기존 `tests/conftest.py`의 환경 격리는 A가 E1 cutover 이후 인수한다(`tests/conftest.py:3-5`). T4는 마지막에 한 에이전트가 덧붙이는 독립 작업이 아니라 각 소유자 테스트와 main의 통합 증거를 IN 표로 모으는 작업이다.

### 4.3 착수 순서

**계약 수정 → E1a namespace 단독 cutover → A(E3a/E2a) → A(E3b/E2b)와 B·C·D·E 병행 → F(E3d/E10) → B의 E9(S1 통과 후) → G의 E1b/E2c 운영 cutover → main 통합 인수.**

S1·S2·S3와 표본/게이트 정리는 이 순서와 병행하되 결과가 필요한 E9/E8b/일반 출시를 앞질러 완료 처리하지 않는다. 모델/노트/제공자 작업은 공통 데이터 계약 확정 후 운영 원본이 아닌 fixture와 개발 루트에서 진행한다.

## 구현 착수 가능/불가 판정

- **현 계약을 ‘고정 계약’으로 M1 전체 구현에 넘기기: 불가.** 특히 R01–R04(저장·소유권), R07–R10(노트 보존), R13–R16(외부 전송·인증)을 구현자 판단에 맡기면 안 된다.
- **즉시 가능한 작업:** main의 계약 수정, E1 이름/공개 경로 cutover 준비, 허가된 v1/노트 fixture 준비, S1/S2/S3 증거 수집. 이는 엔진 기능 완료나 운영 이행 허가가 아니다.
- **수정 후 착수:** 위 4.3 순서. 첫 실제 Mac mini 업그레이드는 DB·설정·서비스·노트 이행을 한 묶음으로 검증한 뒤에만 진행한다.
- **보고 수준:** 이 결과는 정적 검토이며 실행만/가정으로 확인/실제 입력으로 확인에 해당하는 신규 실행 증거는 없다. 제품 게이트의 표본 경로 부재·미결 확인 시각 문제도 닫았다고 보고하지 않는다.
